Subnet Calculator & Cloud Network Planner

Work out IPv4 and IPv6 networks, plan your whole address space, lay out Azure, AWS and Google Cloud networks with each cloud's rules built in, and generate firewall rules and deployment code.

New to IP addressing? Start here

Every device on a network has an IP address: four numbers from 0 to 255 separated by dots, like 192.168.10.57. Behind the scenes it is 32 ones and zeros (bits), 8 for each number.

A subnet is a block of consecutive addresses that belong together, like a street where every house shares the street name. The prefix after the slash (the 26 in /26) says how many of the 32 bits are the street name, called the network part. The bits left over number the houses, called the host part.

Fewer network bits means more host bits, which means a bigger subnet. Every bit given to hosts doubles the size: /24 is 256 addresses, /25 is 128, /26 is 64. That is why subnet sizes are always powers of two.

A subnet mask such as 255.255.255.192 is the same information as the prefix, written like an address: ones over the network bits, zeros over the host bits.

Try changing the number after the slash below and watch the results and the bit ruler change. Each result has a short explanation under it.

Accepts 10.1.2.3/24, 10.1.2.3 255.255.255.0, or 10.1.2.3/255.255.255.0

Split into smaller subnets

Why split a network?

You often get one big block and divide it so different groups (servers, staff laptops, Wi-Fi guests, printers) live in separate subnets. That keeps traffic organised and lets you apply different security rules to each group. Choose a longer prefix to cut the block into equal pieces. In each piece the first address is the network address and the last is the broadcast address, so neither can go to a device.

How Azure networking works, in plain terms

A virtual network (VNet) is your own private network inside Azure. You give it an address space, a big block such as 10.1.0.0/20 (4,096 addresses), and everything you put in the VNet gets an address from that pool.

You then cut the address space into subnets. Virtual machines and services always live in a subnet, and you attach security rules (network security groups) and routing per subnet. Some Azure services insist on a subnet of their own with an exact name and a minimum size; the planner knows those rules and warns you when they are broken.

Azure keeps 5 addresses in every subnet: the first (network address), the second (the default gateway, which is the subnet's router), the third and fourth (Azure DNS) and the last (broadcast). A /24 therefore has 256 addresses but only 251 you can use.

Plan for growth. A subnet that has resources in it is hard to resize, and VNets you want to connect (peer) must not overlap. Use private ranges (10.x.x.x, 172.16 to 172.31.x.x, 192.168.x.x), leave free space, and give every VNet its own separate block.

Hub and spoke is the most common layout. One hub VNet holds shared services: the gateway to your offices, the firewall and Bastion. Each application gets its own spoke VNet, peered to the hub. The example buttons below load one of each.

Virtual network

The name, resource group (a folder that holds related Azure resources) and region (the Azure location, such as westeurope) are only used in the deployment code at the bottom. The address space is what matters for planning: the total pool of addresses that every subnet is carved from.

Subnets

Size each subnet by the number of hosts you need, a prefix length, or an exact CIDR. Azure keeps 5 addresses in every subnet, so host counts are padded automatically. Subnets sized by hosts or prefix are placed largest first so nothing is wasted on alignment.

What the subnet options mean
  • Name is your label. Special Azure subnets need an exact name, so it is filled in and locked for those.
  • Purpose is what will live in the subnet. Picking a special purpose applies its Azure rules: required name, minimum size and recommended size. A description appears under each row.
  • Hosts needed: tell it how many devices or IPs you need. The planner adds Azure's 5 reserved addresses and rounds up to the next allowed size.
  • Prefix length: choose the size directly. /24 = 256 addresses, /25 = 128, /26 = 64, /27 = 32, /28 = 16, /29 = 8, which is Azure's smallest.
  • Exact CIDR: pin the subnet to a specific range, for example to match a network that already exists. It must start on a boundary matching its size (a /26 can start at .0, .64, .128 or .192).

Plan

How to read the plan
  • Allocated is the total size of all subnets. Usable by resources subtracts Azure's 5 reserved addresses per subnet. Unallocated is what is still free for future subnets.
  • The bar is the whole address space from first to last address. Each coloured block is a subnet at its real position and to scale; striped areas are free.
  • Usable range is the addresses Azure can hand out to your VMs and services. Azure reserved shows the 5 held-back addresses; hover to see what each one does.
  • A subnet must start on a multiple of its own size. Placing the largest subnets first avoids leaving unusable gaps, which is why the order can differ from your list.
  • Unallocated space lists the free gaps as the biggest clean blocks you could still create.
  • Red notes are problems that would make Azure reject the deployment. Amber notes are recommendations. The grey text under each subnet explains how it was sized and placed.

    Why overlaps matter
        
    Connected networks send traffic based on the destination address. If two networks both contain 10.1.8.5, a router cannot tell which one you mean. Azure refuses to peer VNets whose address spaces overlap, and VPN connections to an overlapping office network break routing. Check every VNet and office network you might ever connect before choosing ranges; renumbering later is painful.
    
      
    
      
      
    
      
    
    
    
  
    

  
  
    
    
    How AWS networking works, and how it differs from Azure
      
    The subnet math is exactly the same in every cloud: same prefixes, same powers of two, same alignment rules. What changes is each cloud's own rules on top.
    
      
      
        
    • A VPC is AWS's VNet. A VPC (Virtual Private Cloud) is your private network in AWS. Its address range is called a CIDR block.
      • 
        
    • Both clouds keep 5 addresses per subnet, but different ones. AWS keeps the first four (network address, VPC router, Amazon DNS, and one held for future use) plus the last. Azure keeps the first four (network, gateway, two for DNS) plus the last. Same count, so a /24 has 251 usable addresses in both.
      • 
        
    • Size limits differ. An AWS VPC block must be between /16 and /28; for more than 65,536 addresses you add secondary blocks later. The smallest AWS subnet is a /28 (16 addresses, 11 usable), while Azure allows a /29.
      • 
        
    • Availability Zones are the biggest difference. An AWS subnet lives in exactly one Availability Zone, a separate datacenter within the region. To survive a datacenter failure you create each tier once per zone, so a 3-tier app across 3 zones needs 9 subnets. An Azure subnet automatically covers every zone in its region, so one per tier is enough. This planner repeats each tier across the zones you choose.
      • 
        
    • Public or private is a routing choice. An AWS subnet is public when its route table sends internet traffic (0.0.0.0/0) to an Internet Gateway. Private subnets reach the internet through a NAT gateway placed in a public subnet. Azure has no public/private subnet split like this.
      • 
        
    • No special subnet names. AWS does not demand exact names like Azure's GatewaySubnet, but some services still want small dedicated subnets in each zone, such as Transit Gateway and Network Firewall.
      • 
      
    
    
    

    
    
      
    VPC

Availability Zones is how many separate datacenters each tier is spread across; 2 or 3 is typical for production.

      • 
        
    • Prefix length sets each zone's subnet size directly. /24 = 256 addresses, /26 = 64, /28 = 16, which is AWS's smallest.

      How IPv6 differs from IPv4
      
      IPv6 addresses are 128 bits long instead of 32. They are written as eight groups of four hexadecimal digits (0–9 and a–f) separated by colons, such as 2001:0db8:0000:0012:0000:0000:0000:0001.
      
      
      Two shortcuts make them shorter. Leading zeros in a group can be dropped (0db8 becomes db8), and one run of all-zero groups can be replaced by a double colon. So the address above is normally written 2001:db8:0:12::1. The double colon may appear only once, otherwise nobody could tell how many zeros each one stands for.
      
      
      The prefix works exactly like IPv4: /64 means the first 64 bits are the network. The difference is scale. One /64 holds about 18 quintillion addresses, so IPv6 subnets are never sized by host count. Almost every subnet is a /64, because devices create their own address automatically (called SLAAC), and that needs 64 host bits.
      
      
      IPv6 has no broadcast address (multicast does that job) and rarely uses NAT, because there are enough addresses for every device to have its own. Firewalls, not NAT, keep devices private.
      
      
      In the cloud, Azure and Google Cloud subnets use /64s, and AWS gives each VPC a /56 (room for 256 /64 subnets) by default.
      
    
      
    
      
      
      
      
      Accepts full or shortened forms, like 2001:db8::1/48 or fd00:0:0:1::/64
      
      
      
      
      
      
      
    
      
    
      
      
      Split into smaller prefixes
      
      
      How IPv6 space is usually divided
        
      A typical organisation gets a /48 from its provider or region. That alone holds 65,536 /64 subnets, more than most companies will ever need. A common pattern is to split on 4-bit boundaries, one hex digit at a time: /48 for the organisation, /52 per site, /56 per building or VPC, /64 per subnet. Each step then changes exactly one hex digit, which keeps addresses easy to read.
      
      
      
      
      
        
      
        
      
      
      
      
      
      
      
      
      
    
      
  
      

  
  
      
    
      
      
      Summarise routes
      
      
      What route summarisation is
        
      Summarising means describing many networks with fewer, bigger blocks. A VPN or firewall that lists 10.1.0.0/24, 10.1.1.0/24, 10.1.2.0/24 and 10.1.3.0/24 can list 10.1.0.0/22 instead, because those four blocks sit side by side and together fill exactly that /22. Fewer routes means simpler configuration, smaller routing tables and fewer mistakes. It only works cleanly when blocks are next to each other and aligned, which is why a careful address plan pays off.
      
      
      
      
      
      
      
    
      
    
      
      
      Which range is this address in?
      
      
      How routers decide when ranges overlap
        
      An address can sit inside several ranges at once: 10.1.2.37 is inside the VNet 10.1.0.0/20 and also inside the subnet 10.1.2.0/25. Routers and firewalls then use longest prefix match: the most specific range, the one with the biggest number after the slash, wins. That is how a cloud can send a whole network one way and a single subnet inside it another way.
      
      
      
      
      
        
      
        
      
          
      
      
      
      
      
      
      
    
      
  
      

  
  
      
    
      Why plan your whole address space first
      
      Every network you might ever connect, whether offices, Azure VNets, AWS VPCs or Google Cloud, needs addresses that do not overlap. Otherwise they cannot be joined later without painful renumbering. An address plan hands out big, non-overlapping blocks up front, one per cloud, region and environment, and each team then carves its own subnets from its block.
      
      
      Good plans keep related networks together in one aligned block, so each group can be reached with a single route, and leave plenty of space free for growth. 10.0.0.0/8 holds 16.7 million addresses; giving each environment a /16 (65,536) is common and still leaves room for 256 of them.
      
      
      Enter what already exists as exact ranges so the plan works around them, then add blocks for everything new. When a cloud block is ready, open it straight in the matching cloud planner.
      
    
      
    
      
      
      Address space
      
      
      
      
      Usually one of the private ranges: 10.0.0.0/8 (16.7 million addresses), 172.16.0.0/12 (1 million) or 192.168.0.0/16 (65,536). Larger organisations normally use 10.0.0.0/8.

        How Google Cloud networking works, and how it differs
          
      
        • The VPC is global. One Google Cloud VPC network spans every region and has no address space of its own. Each subnet has its own range and lives in one region. Azure VNets and AWS VPCs, by contrast, sit in a single region and have an overall address space.
          • 
      
        • Subnets are regional, as in Azure and unlike AWS: one subnet covers every zone in its region, so you do not repeat it per zone.
          • 
      
        • Google keeps 4 addresses per subnet, not 5: the first (network), the second (default gateway), the second-to-last (reserved for future use) and the last (broadcast). The smallest subnet is a /29 (8 addresses, 4 usable).
          • 
      
        • Secondary ranges. A subnet can carry extra ranges, mainly for Kubernetes (GKE) pods and services. They come from your address plan too and must not overlap anything.
          • 
      
        • Special ranges exist for regional load balancers (proxy-only subnets), Serverless VPC Access connectors (exactly /28) and private services access for managed services like Cloud SQL.
          • 
      
        • The planning block below is not a Google Cloud setting. It is the range you set aside for this VPC in your address plan, so subnets in every region stay inside it and never clash with your other networks.
          •

          How cloud firewall rules work
      
          Firewall rules decide which traffic may reach your resources. Each rule matches a source (where traffic comes from), a destination (where it is going), a protocol (TCP, UDP or ICMP) and a port (which service, such as 443 for HTTPS), and then allows or blocks it.
          
      
          All three clouds use stateful rules: once a connection is allowed in, its replies are allowed back out automatically, so you only describe who may start a connection.
          
      
          Good practice is least privilege: allow only the sources and ports that really need it, and never open management ports such as SSH (22) or Remote Desktop (3389) to the whole internet.
          
      
          The clouds differ in the details. Azure network security groups (NSGs) use numbered priorities and support allow and deny. AWS security groups can only allow, so blocking needs a network ACL. Google Cloud firewall rules apply to the whole VPC and use priorities like Azure.

          IPv4 prefix reference
          
      
          Azure and AWS usable = addresses minus the 5 each cloud reserves; Google Cloud reserves 4. Azure subnets can be no smaller than /29, AWS subnets no smaller than /28.
          
      
          What each column means
            
        
          • Prefix: how many of the 32 bits are the network part, written after the slash.
            • 
        
          • Netmask: the same prefix written as an address. Some devices and older tools want this form.
            • 
        
          • Wildcard: the mask with ones and zeros swapped. Cisco access lists and some firewall rules use it.
            • 
        
          • Addresses: the total size of the block, always a power of two.
            • 
        
          • Usable hosts: in a normal network, total minus 2 (network and broadcast addresses). /31 is a special case for links between two routers and /32 means a single address.
            • 
        
          • Azure usable: total minus 5, because Azure reserves 5 addresses per subnet.
            • 
        
          • Google Cloud usable: total minus 4, because Google reserves 4 addresses per subnet. Its smallest subnet is /29, like Azure.
            • 
        
          • AWS usable: also total minus 5, because AWS reserves 5 too. The difference is that AWS stops at /28, so a /29 is not possible there.
